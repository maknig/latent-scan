# latent-scan

Standalone film-scanning module for [latent](../latent) (Rust, egui archive of films and
enlargements). Built to be merged into latent later: crates here become workspace members there.

## Commands
- `nix develop` for the toolchain and `scanimage` (sane-backends).
- `cargo test --workspace`, `cargo clippy --workspace --all-targets`, `cargo fmt`.
- `cargo run -p latent-scan-cli -- list | caps | profiles | scan -p <profile> [--archive DIR --table T --id N | -o FILE]`
- `cargo run -p latent-scan-gui` for the GUI (saves to the folder used last, `~/Pictures/latent-scan` at first); `cargo run -p latent-scan-gui -- <archive>` starts in that latent archive.

## Layout
- `crates/latent-scan-core`: types and the `Scanner` / `ScannerBackend` traits. No I/O.
- `crates/latent-scan-sane`: SANE backend driving `scanimage` (Canon `pixma`, Epson `epson2`/`epsonds`). Parsers are tested against `tests/fixtures/`.
- `crates/latent-scan-profiles`: named presets from `profiles.toml` (source, colour, depth, dpi, area in mm).
- `crates/latent-image-edit`: **all pixel edits, no UI, nothing scanner-specific** (latent shares it): `RawImage` (16-bit samples), its own `Error`, the `Stage` trait and `Pipeline`, `tone` (negative, levels, `Adjust` incl. saturation), `sharpen`, `clarity`, `heal` (dust), crop / rotate / invert, TIFF/PNG/JPEG read and write (`BitDepth`, `OutputFormat`). `latent-scan-core` re-exports `RawImage` and converts the error.
- `crates/latent-image-edit-ui`: egui front end of it, again without any scanner knowledge: the `Editor` window (see "Image editor"), `sliders` (grouped image sliders, preset bar), `presets`, `form`, `canvas`, `view`, `crop` (overlay and view maths), `dust`, `histogram`, `preview` (render and downscale helpers), `edit` (backup and restore). Hosts own an `Editor`, call `sync` and `show` and react to `EditorEvent`.
- `crates/latent-scan-archive`: latent folder layout `images/<table>/<id:04>/<file>` and appending to a row's `images` list in `latent.data.json`. On disk `images` is a JSON array of paths (latent only joins it with newlines in memory; a plain string fails to load with "bad json value"); `add_image` also converts such a string into a list. Mirrors `latent_data::fs::import_image`; keep in sync.
- `crates/latent-scan-detect`: fits preset frames to the film (see "Auto-adjust"); pure, depends on `latent-scan-core` only.
- `crates/latent-scan-ui`: egui UI (`ScanUi`). `show_main(ctx)` fills the standalone app's window (resizable controls left, preview right, image strip bottom); `open`/`show(ctx)` is the floating window for embedding. Files: `lib.rs` (state and logic), `panels.rs` (controls, sliders, preview pane), `strip.rs` (image strip, large view), `thumbs.rs` (thumbnail cache), `settings.rs` (remembered settings), `frames.rs` (`crop_to_mm`: frames on the bed in mm), `preview` and `crop` come from `latent-image-edit-ui`, `targets.rs` (rows and a row's images from `latent.data.json`), `worker.rs` (jobs on threads over an mpsc channel). Depends on `egui`; `latent-scan-detect` stays free of it.
- `apps/latent-scan-cli`: the `latent-scan` binary.
- `apps/latent-scan-gui`: the `latent-scan-gui [archive]` eframe app hosting `ScanUi`.

## Conventions
- Backends only talk through `latent-scan-core` traits; nothing outside `latent-scan-sane` knows about SANE.
- Library errors are `thiserror` enums; the binary prints `error: ...` and exits 1.
- With pixma, set `--source` before mode and resolution (it resets them).
- A profile may carry `scanner = "<part of the model name>"` (`Profile::fits`, `Profiles::for_scanner`): the GUI lists only profiles that fit the selected scanner and tags profiles it saves with that scanner; untagged profiles fit every scanner. Built-ins are tagged `9000F` (Canon) and `X980` (Epson V800).
- Film-holder areas in `profiles.toml` are approximate and need calibrating. Epson V800 (sold as GT-X980, `epson2`): depth is a separate `--depth` option (set after `--mode`, `SourceCaps::depths`); the `TPU8x10` source is ignored; transparency window 149.86 x 246.38 mm; fixtures `tests/fixtures/epson_v800_options*.txt`; `epson-*` profile areas are guesses to calibrate.
- Overview scans set `ScanJob::preview`; where the device has a `--preview` option (`SourceCaps::quick_preview`, Epson) `scan_args` adds `--preview=yes`: the V800 backlight scan of 100 mm at 150 dpi takes 15 s instead of 23 s (75 dpi: 10 s). Real scans and the pre-scan adjust never use it.
- 16-bit samples throughout; never downconvert before writing (JPEG, 8 bit by nature, is the one file format that cannot hold them).

## Embedding into latent
- Add the `scan-*` crates as native-only workspace members (`cfg(not(wasm32))`, like `vision`); add a File > "Scan..." item that calls `ScanUi::open(ctx, Some(Target { table, row_id }))` and `ScanUi::show(ctx)` each frame.
- latent keeps the store in memory, so construct with `.write_data(false)` and call `add_images` from `ScanEvent::Saved`; otherwise reload after the event.
- `latent-image-edit-ui/src/crop.rs` mirrors `crop_overlay` in latent's `lib.rs`; extract one shared helper when merging.
- UI strings are English constants (`text` module in `latent-scan-ui/src/lib.rs`); latent plans German later.
- Cancel: `CancelToken` is passed to `Scanner::scan`; the SANE backend sends SIGTERM to `scanimage` (SIGKILL after 10 s).

## Scanner behaviour (Canon 9000F, measured)
- Options differ per source: `Capabilities` holds one `SourceCaps` per source. Flatbed offers 75–4800 dpi and `48 bits color` / `16 bits gray`; the transparency unit offers 300–9600 dpi and only `Color` / `Gray` / `Infrared`, which deliver 16-bit samples. `pick_mode` falls back to the plain mode.
- The transparency window is about 216 x 250.6 mm although `-y` reports 297 mm; the scanner clips. The GUI therefore derives the preview's size from the pixels delivered (`delivered_area` in `latent-scan-ui/src/worker.rs`).
- Flatbed 48-bit scans at 75 dpi come back at 150 dpi (driver minimum).
- 600 dpi A4 16-bit is ~215 MB; `read_tiff` decodes without the image crate's allocation limit.

## Calibrating film-holder areas
1. `cargo run -p latent-scan-gui -- <archive>`, select the profile (e.g. `35mm-strip`), put the holder in, press Preview (whole transparency window).
2. Drag the frame onto the frame area, type a name under "Save profile" and press its button.
3. Stored per user in `~/.config/latent-scan/profiles.toml` (`$XDG_CONFIG_HOME` honoured); same-named profiles override the built-in ones from `crates/latent-scan-profiles/profiles.toml`.

## Frames and batch scans
- A profile can hold several frames (`Profile::frames`, mm on the bed, scan order). `area` stays as the first frame for old files; `frame_areas()` / `jobs()` give one entry per frame.
- GUI: on the overview preview, "Add frame" puts a new frame next to the active one (same size, along the longer side); drag a frame to select and move it, drag its edges to resize, "Delete frame" removes it. "Save profile" stores all frames. Dimming is only drawn for a single frame.
- Scan runs one scan per frame at full dpi (`worker::run_batch`, tested with a fake `Scanner`). Files are `<prefix>-<NN>` from `latent_scan_archive::naming::frame_stem`, numbered from "Start no."; the start advances by one per saved frame. A failed or cancelled batch keeps the frames already saved.
- `ScanUi::show` returns `Vec<ScanEvent>` (one `Saved` per frame).
- CLI: `scan -p <profile> --name <prefix> --start N --archive DIR --table T --id N` scans all frames of the profile; `-o` is only for single-frame profiles. Without `--start` a single frame is stored as `<name>.tiff`.

## Tone, colour mode and formats
- `latent_image_edit::tone`: `Tone::estimate(reference, ToneOptions)` + `Tone::apply`, and `ToneStage` (estimate from the image itself) for the scan pipeline (`Rotate -> ToneStage`).
  - **Negative**: per channel `1 - v/base`, base = 99.5th percentile of the reference (the thinnest density). Equalises the channels' bases, which removes the orange mask; plain invert for gray. Heuristic: a frame without any thin-density area is balanced slightly off.
  - **Auto levels**: per channel stretch of the 0.1th–99.8th percentile to the full range, after the negative step. Off by default so archive scans stay untouched.
- The GUI keeps the overview preview as a display-sized 16-bit `RawImage` and re-renders its texture (`preview::render`) when negative / auto exposure / colour mode change, the active frame changes or a drag ends. The tone is estimated from the active frame only and applied to the whole overview, so the preview shows what that frame's scan will look like. Preview scans are always colour; Gray is applied as luma in the display step.
- Colour mode (Colour / Gray) and the negative flag live in profiles (`color`, `negative`). B&W film = Gray + negative; on the transparency unit Gray falls back to the plain `Gray` mode, still 16-bit.
- Output is 16-bit TIFF or PNG, or 8-bit JPEG (`OutputFormat`, `write_image` picks the format from the extension; JPEG is written at quality `JPEG_QUALITY` = 95 and ignores the depth asked for, the Bit depth row then reads "8 bit (JPEG is always 8 bit)"). CLI: `--format png|jpg --negative --auto-levels --gray`.

## Auto-adjust (`latent-scan-detect`)
- Holder and film shift between sessions, so preset frames are re-fitted: `fit_frames(img, window, presets, &Options)` moves each preset's rectangle outline (size unchanged) to where its four edges best match strong brightness edges (Sobel on blurred luma, gradients clipped at the 90th percentile of the strong ones, prefix sums so an edge costs O(1), absolute gradient so negatives and slides both work). A strip gets one shared shift (±`search_mm` = 3 mm) first, then each frame is refined ±`refine_mm` = 1 mm. No Hough: the outline match is simpler, has a confidence, and weak matches keep the preset.
- Confidence = peak prominence over the search window × edge strength relative to the image's mean gradient. Below `min_confidence` (0.25) a frame follows the strip's shift, or stays put when the strip match is weak too. Tunables are in `Options::default()`; tune from real film results.
- `Options::inset_mm` (GUI "Margin"): if the saved frames lie inside the visible frame boundary, set how far; the outline that is matched is the preset grown by it, the result is shrunk again. Without it a preset inset from the boundary has edges on both sides that pull in opposite directions.
- GUI: **Auto-adjust frames** fits the frames on the current overview (not saved unless "Save profile"); **Adjust frames before scan** runs `adjust_before_scan` per frame (600 dpi 8-bit pre-scan of the frame plus 5 mm margin, clamped to the source's `max_area`) inside `worker::run_batch` and reports each result in the status line. CLI: `scan --adjust`.
- Limits: no rotation correction, no size change. Strong structure near the frame (holder window, bed edges) attracts the match; the holder aperture is a legitimate target but check the result by eye the first times.

## Main window, strip and settings
- `apps/latent-scan-gui` calls `ScanUi::show_main`: `TopBottomPanel::bottom` (strip, resizable), `SidePanel::left` (controls, resizable 240–560 px), `CentralPanel` (preview). eframe's `persistence` feature remembers window and panel sizes. The controls are collapsing sections in workflow order, top to bottom (Scanner & profile, Auto-adjust frames, Save profile, Image, Save to); Preview / Scan / Cancel with the progress bar, status line and file-name range are a bar **pinned at the bottom** of the panel (`TopBottomPanel::bottom(..).show_inside`; the floating window puts it under the scrolling settings). The frame controls (Add/Delete, the selector, rotate ⟲ ⟳) are one `horizontal_wrapped` line **above the preview** (`panels::frame_bar`) that only breaks when the pane is too narrow; the active frame's size is in the info line under the preview.
- **Image strip**: the images of the row chosen under "Save to", read from `latent.data.json` (`targets::row_images`, reloaded on target change, after each save and with ⟳). Tiles show 320 px thumbnails (click selects, double click opens the image editor, right-click: Open (editor) / Copy path). Thumbnails decode on 2 worker threads (`thumbs.rs`, `ImageReader::no_limits`; a 215 MB 16-bit scan takes ~0.3 s) and are cached in `<archive>/.thumbs/<size>/<hash>.png` with the **same key as latent** (hash of path, length, mtime), so both programs reuse them. After a scan the worker writes the 320 px cache thumbnail from the in-memory image, so the new tile appears at once. Merge note: extract a shared helper with latent's `images.rs`.
- **Settings** (`settings.rs`): the auto-adjust values (search range 0.5–8 mm, refine 0–3 mm, min. confidence 0–1, margin 0–3 mm) are sliders, remembered in `<config dir>/settings.toml` (`latent_scan_profiles::config_dir`, written when the slider is released). Image sliders are not remembered: they reset with each new preview.
- **Image sliders** (`latent_image_edit::tone::Adjust`, part of `ToneOptions`, so they apply to the preview and to the saved scan; neutral = untouched, byte-identical): exposure ±2 EV, black point 0–40 %, white point 60–100 %, midtones (gamma) 0.5–2, warm/cool and tint (colour only). Applied after negative and auto levels. `Tone::apply` uses one 65536-entry lookup table per channel; `Tone::with_adjust` swaps only the adjustment. The preview re-renders live while a slider moves (the estimate comes from the active frame only, so it is cheap). CLI: `--exposure --black --white --midtones --warmth --tint`.

## Per-frame adjustments and Auto
- The image sliders belong to a frame: `ScanUi::adjusts` is a `Vec<Adjust>` kept the same length as `frames`. Selecting a frame shows and edits its values and re-renders the preview with them; "Add frame" copies the active frame's values, "Delete frame" removes its entry, choosing a profile or getting a new preview resets everything to neutral. `worker::Frame::adjust` carries each frame's values into `run_batch`, so every scan is saved with its own adjustments (applied after the request-wide negative setting). Not stored in profiles.
- **Auto** (`Adjust::auto_levels`) no longer hides a per-channel stretch: it measures the frame's pixels on the overview (0.1th and 99.8th percentile of all channels pooled, after the negative step when negative is on), limited to the slider ranges, and **writes black and white point into the frame's sliders**, so the saved scan equals what the sliders show and the result can be tweaked. Buttons: `Auto` (active frame), `Auto all` (each frame on its own area), `Reset` (active frame), `Copy to all`. The old "Exposure: auto" checkbox is gone from the UI; `ToneOptions::auto_levels` (per-channel) remains for the CLI (`--auto-levels`).

## Rotation
- One rotation (0/90/180/270, clockwise) turns the preview **and** the saved scans: `ScanUi::rotate`, buttons ⟲ ⟳ above the preview, `Rotate` stage in the worker. It is stored in profiles (`Profile::rotate`, default 0) and set when a profile is selected; the CLI `--rotate` defaults to the profile's.
- Frames stay in bed coordinates (normalized to the unrotated overview, mm via `crop_to_mm`). The preview texture is rotated in `preview::render` (`rotate_image`), and frames are edited in view space: `crop::to_view` / `from_view` convert before and after `crop::overlay`, and only a changed view is written back.

## Checking a scan against its preview
- After each frame the GUI compares the saved scan with the overview it was placed on (`latent_scan_detect::compare_with_overview`, `worker::check_text`): size from the pixels vs the asked size, and the scan's position (mm) and length scale per axis on the overview (shrunk to the overview's resolution, normalized cross-correlation over +-2 mm and scale 0.97..1.03). The status line shows e.g. `Saved frame-03: asked 56.52 x 68.39 mm, got 56.52 x 68.39 mm; position vs preview +0.17 / -0.08 mm, length x1.000 / x1.006` and turns red when something is off by more than 0.15 mm; `LATENT_SCAN_TRACE=1` also prints it. Length scale > 1 along y means the scan covers more of the bed than its preview frame showed. The CLI prints asked vs got size only (it has no overview). Measured so far: the scanner returns the requested length to the pixel, so a difference points at the preview-to-bed mapping (origin/scale of the overview), not at the request.

## Scan offset
- The scanner starts a full-resolution scan a little away from where the preview started (measured on the 9000F: a constant ~0.7 mm along the carriage axis, size and scale exact), so a frame placed on the preview is scanned slightly off. `offset.rs`: every check's error (scan position minus requested area, only matches with correlation >= 0.8 and |error| <= 3 mm) is collected per key (source, preview dpi, scan dpi), the last five are kept, and **minus their median** is added to every request of that key (`ScanRequest::offset`, applied in `run_batch` after the optional pre-scan fit, x/y clamped to >= 0; the frames in the view and the preview scan are never shifted). Plus **Offset X / Y** sliders (Scanner & profile, +-3 mm) to fine-tune by hand and a "Forget learned offset" button. Remembered in `settings.toml` (`[offset]`). The check line shows the position against the frame **in the view**, so it should read about 0 once learned, followed by `offset applied` and, with the pre-scan adjust, `pre-scan fit moved it`. With rotate 90/270 the view's horizontal axis is bed Y.
- If the position error still grows with the frame's Y position after learning, the preview also has a scale error; the per-axis length scale of the check line shows it and a gain along Y would be the next parameter.

## Threads and slow frames
- Nothing heavy runs in a UI frame. Scans, previews, discovery, thumbnails, the editor's image decode and Apply/Backup/Restore are worker threads; so are the **preview renders** (`latent-scan-ui/src/rendering.rs`: `PreviewRenderer`, and `Renderer` in the editor) and **Auto-adjust frames** (`worker::fit_frames`, reported as `Msg::Fitted`). The render threads keep only the newest request ("latest wins") and answer with a finished image; until then the old texture stays on screen (the editor's state line says "rendering…"). Results carry a serial/generation so a late answer for an older picture is ignored. The compositor's "not responding" dialog means a frame blocked for seconds.
- **Hidden windows**: the standalone app runs with `vsync: false`. With vsync the EGL swap waits for the compositor's frame callback, which a window on another workspace never gets, so redraws requested during a scan (progress) stalled the event loop in the swap and Hyprland reported "not responding". `Reporter::send` also throttles progress redraws (`repaint_delay`: 100 ms, 1 s when the window is not focused); other messages repaint at once. `LATENT_SCAN_VSYNC=1` turns vsync back on (tearing on X11).
- `LATENT_SCAN_TRACE=1` prints steps slower than 100 ms to stderr (`latent_image_edit_ui::trace::timed`: the main window frame, preview and editor renders, auto-adjust).
- The pixel crates (`latent-image-edit`, `-ui`, `latent-scan-detect`) are built with `opt-level = 3` even in the dev profile (workspace `Cargo.toml`), and `sharpen::blur` pads rows instead of clamping each tap.

## Where scans are saved
- `ScanUi::standalone(archive_arg)` (the app) offers two destinations (`settings::SaveMode`): **Folder** (default `~/Pictures/latent-scan`, created on first save; plain files `<prefix>-<NN>.<ext>`, clashes get `-n` via `latent_scan_archive::folder_target`) and **Latent archive** (browse for the archive root, accepted only with a `latent.data.json` inside, then pick table and row; files go to `images/<table>/<id>/` and into the row's `images` list). Choosing the archive radio with none chosen opens the browser at once. `ScanUi::new(archive)` (a host such as latent) is archive-only: no switch, no browse.
- Folder dialogs are `rfd` (xdg-desktop-portal backend on Linux, no GTK needed) on a thread (`worker::pick_folder`), answered as `Msg::Picked`.
- Remembered in `settings.toml` `[save]` (`mode`, `folder`, `archive`); an archive argument on the command line wins for that session. The film (table, row) is not remembered.
- `worker::Dest` (`Folder { dir }` | `Archive { root, table, row_id, write_data }`) replaces the old archive fields of `ScanRequest`; `Msg::Saved(SavedTo)` becomes `ScanEvent::Saved { table, row_id, rel }` (archive) or `ScanEvent::SavedFile { path }` (folder).
- The strip lists the folder's image files (oldest first) in folder mode, the row's images in archive mode. Thumbnail cache: `<archive>/.thumbs` (shared with latent) or `$XDG_CACHE_HOME/latent-scan/thumbs` for plain folders, so user folders stay clean.

## Form layout rule (`latent-image-edit-ui/src/form.rs`)
- Every labelled control of the panels is a row of `form::form(ui, id, |f| ...)`: label column of fixed width (`LABEL_W`, longer labels are truncated, never wider) then the input filling the rest of the row. Rows: `combo` (dropdowns all as wide as the row), `slider` (no built-in text; track plus number box fill the row, `SliderOpts` for suffix/decimals/step/log/enabled), `text`, `number`, `check`, `value` (read-only, truncated, full text on hover), and `row` for anything custom (e.g. the scanner dropdown with its ⟳ button).
- Button rows use `form::button_row` (equal-width buttons filling the row). Do not add ad-hoc `Grid`s, `Slider::text` labels or fixed-width dropdowns; new controls go through `Form` so labels and inputs stay aligned.
- Buttons under a form (Save profile, Auto / Reset, Browse…, preset Save / Delete) use `form::form_buttons`: same equal-width row, but indented by `form::input_indent()` so it starts and ends where the inputs do (label column empty). Only the pinned Preview / Scan / Cancel bar and dialogs use the full-width `button_row`.
- **Double-click a slider to reset it**: pass the default with `SliderOpts::default_value(..)` (in the slider's own units, e.g. percent for black/white point); take it from the owning type (`Adjust::default()`, `DetectSettings::default()`, `Sharpen::default()`), never a literal. The hover text then says "Double-click: reset to ...". egui's `Slider` senses only drags, so `response.double_clicked()` is never true for it; `Form::slider` asks `pointer.button_double_clicked` while the pointer is over the slider (`form::reset_on_double_click`). Tests drive this with `form::test_support::Harness` (headless frames with simulated pointer events; let a grid settle for three frames before measuring row positions).
- egui's text field reports its *inner* rect (4 px frame margin outside); `form.rs` tests account for it.

## Zoom (`latent-image-edit-ui/src/view.rs`)
- **Zoom to frame** (toggle in the frame bar) fills the preview pane with the active frame plus 25 % margin, using the overview's pixels (no extra scan, so it softens when zoomed far in). It follows the active frame and the rotation while the zoom was set by that button; editing a frame's edges does not move the view. Mouse wheel / pinch zooms at the pointer, middle or right button drag pans; either ends following. Zooming out to 1× returns to the fitted view (the picture centred in the pane, which keeps its size: `canvas::show` never shrinks the pane, so nothing around it moves while zooming); a new preview or a new set of frames resets it.
- Maths lives in `view.rs` (pure, tested): `ZoomState { center, zoom, follow }` in *view space* (normalized coordinates of the rotated picture); the visible `window` is derived from the pane's shape (`view::shape`), so resizing the pane never distorts. `crop::overlay` takes that window and maps pointer and frames through `to_screen` / `from_screen` / `screen_delta`; edits stay limited to the whole picture, not just the visible part. The picture is drawn with `uv = view::visible(window)`.

## Contrast, Darks, Whites
- `Adjust` (per frame, Image section) has `contrast`, `darks` and `whites`, each -1..1, neutral 0. They shape the tone curve *after* levels and gamma (`Adjust::map` -> `Adjust::shape`): darks and whites add `0.14 * slider *` a smooth bump that peaks at 1/3 (darks) or 2/3 (whites) and vanishes at black and white; contrast adds `slider * x(1-x)(2x-1)`, a cubic S-curve around mid-grey. Black and white map to themselves and the curve stays monotonic over the whole slider range (a grid test proves it). Difference to Black/White point: those clip and stretch the ends, Darks/Whites change how bright the shadows/highlights are without clipping. Auto still sets only black and white point. CLI: `--contrast --darks --whites`. The constants (0.14, cubic) are the first thing to tune from real film.

## Image editor (`latent-image-edit-ui/src/editor.rs`), grouping and sharpening
- Double-click a tile of the strip: an image view like latent's with a toolbar (◀ ▶ i/n, zoom out/fit/in, ⟲ ⟳, Crop, **Apply**, Revert, **Backup original**, **Restore original**), the picture on the left (wheel zoom, middle/right-drag pan, double-click = fit, crop overlay; `canvas.rs` and `view.rs` are shared with the scan preview) and a 300 px side column: RGB **histogram** (`histogram.rs`; grey for gray images; the two end bins are ignored for scaling), Film negative, the image sliders in Lightroom-like **groups** (`sliders::adjust_groups`, see below), a Save-as-8-bit box and `Auto` / `Reset sliders`. Arrow keys step, Esc closes; stepping or closing drops unsaved edits and says so.
- **Preview first**: every change only affects the preview (a 2048 px 16-bit copy, decoded on a worker thread with `latent_image_edit::read_image`); the crop is an overlay until applied. `Edits { negative, adjust, clarity, sharpen, turns, crop, spots, eight_bit }` is what is pending (`Edits::is_neutral`); rotation and crop are stored in the file's orientation and edited in view space (`crop::to_view/from_view`).
- **Apply** (worker thread, `editor::apply_file`): full-resolution decode -> `Crop` -> `Rotate` -> `ToneStage` -> `ClarityStage` -> `SharpenStage`, written atomically (hidden temp file with the same extension, then rename, `edit::overwrite_atomic`), same format, 16-bit kept; the strip thumbnail is rewritten, the editor reloads. **Apply never backs up silently**: with no backup it asks (`Back up and apply` / `Apply without backup` / `Cancel`). `Backup original` copies the file to `<root>/.originals/<relative path>` (latent's layout, `edit.rs`; only if none exists), `Restore original` copies it back and removes it, so latent's own Restore also works on these files. TIFF, PNG and JPEG are editable (a JPEG stays an 8-bit JPEG, re-compressed by every Apply, and the no-backup prompt says so); other files are view-only.
- **Host API** (`Editor`, no `ScanUi` involved): the host calls `editor.sync(ctx, root, &files, index)` every frame with the wanted file (paths relative to `root`, where backups go: `<root>/.originals/`) and `editor.show(ctx, &mut PresetUi)`, which draws the window and returns `EditorEvent`s: `FileChanged { path, image }` (an Apply wrote `image`, or a Restore rewrote the file with `None`: refresh thumbnails), `Selected(i)` (user stepped), `Closed`. The editor owns its worker threads and channel and shows its status in the window. `ScanUi::editor_window` (strip.rs) is the scan host: strip selection drives `sync`, `FileChanged` forgets and rewrites the strip thumbnail.
- **Slider groups** (`sliders::adjust_groups`, shared with the scan panel): collapsing headers **Light** (Exposure, Contrast, Darks, Whites, Midtones), **Levels** (Black point, White point), **Colour** (Warm / cool, Tint, Saturation) and, when clarity and sharpening are passed (editor only), **Detail** (Clarity, Sharpen, Radius). A header shows a small reset button while its group differs from the default. The groups are also available as plain rows (`light_rows`, `levels_rows`, `colour_rows`, `detail_rows`) for hosts that lay them out themselves.
- **Saturation** (`Adjust::saturation`, -1..1, part of the per-frame sliders so it also applies to scans): after the tone lookup, each channel moves away from the pixel's luma (`luma + (c - luma) * (1 + s)`, Rec. 709 weights, clamped); -1 is gray; gray images ignore it. CLI `--saturation`.
- **Clarity** (`latent_image_edit::clarity`, `Clarity { amount }` -1..1, editor only): local contrast in the midtones. Luma minus a very smooth copy of itself (Gaussian, sigma = 2 % of the longer side, computed on a shrunk plane so it stays cheap on 100 MP files), weighted by `4 l (1 - l)` so black and white never move, added to every channel. Because the radius follows the image size, the 2048 px preview matches the full file closely. Negative softens. The constants (2 %, weight, gain 1) are the first thing to tune from real film.
- **Sharpening** (`latent_image_edit::sharpen`): unsharp mask on brightness only (luma blurred with a separable Gaussian, sigma = radius; `amount * (luma - blur)` added to every channel, clamped), so colours do not fringe. It is spatial, so not part of `ToneOptions`; the preview scales the radius by preview/file size (`Sharpen::scaled`) and is therefore only approximate; judge fine detail after Apply (Restore original undoes it). Sharpening exists only in the editor, not at scan time.

## Presets (`latent-image-edit-ui/src/presets.rs`)
- Named slider sets: the `Adjust` values (incl. saturation) plus clarity and sharpen amount/radius (older files without the newer keys still load) (not Film negative, crop or rotation). Stored in `<config dir>/presets.toml` (`[[preset]]`, written atomically); loaded values are clamped to the slider ranges, a broken file gives none plus a warning.
- Built-in **"Default"** (all neutral, first in the list; loading it resets sliders and sharpening) and **"SilverFast look (FP4)"** (exposure +0.10, contrast +0.20, darks -0.20, whites -1.00, midtones 0.83, sharpen 0.5/1.0), fitted to film 71 against its SilverFast scans; a user preset of the same name overrides it, deleting that restores the built-in. Built-ins cannot be deleted.
- UI: `sliders::preset_row` (dropdown, name field, Save / Delete preset) sits above the sliders in the scan panel's Image section (loads into the active frame; sharpening ignored, an existing preset's sharpening is kept when saving there) and in the editor's side column (loads sliders and sharpening into the preview; Apply stays explicit). `ScanUi::presets` (`PresetUi`) is shared by both. No CLI option (`latent-scan-cli` does not depend on `latent-scan-ui`).

## Dust removal (`latent-image-edit/src/heal.rs`, `latent-image-edit-ui/src/dust.rs`)
- Port of latent's dust tool (`heal` in latent's `images.rs`; keep both in sync) to 16-bit gray/RGB `RawImage`: each `Spot { x, y, r }` (fractions of the file's width/height, radius as a fraction of the width) is filled by copying the nearby texture that best continues its surroundings (grain included), feathered at the edge, flat median fill as fallback. `HealStage` is the `Stage`.
- In the image editor it is a pending edit like the others: **Dust** toggle next to Crop (the two modes exclude each other), brush **Size**, **Undo**, **Clear (n)**; click or drag on the picture marks spots (left button; wheel zoom and middle/right pan still work). `Edits::spots` holds them in the *file's* orientation (`dust::spot_from_view` / `spot_to_view` convert for the turned picture), so `Edits` is `Clone`, not `Copy`.
- Preview: `EditorState::refresh` heals the 2048 px base only when the spot list changed (cached in `healed`) and waits while the mouse is down (`painting`). **Apply** (`apply_file`) heals first, on the untouched full-resolution file, then crop -> rotate -> tone -> sharpen; 16 bits are kept (latent's is 8-bit). Backup/Restore original work as for the other edits.
- Not done: scan-time removal, the scanner's infrared dust channel, automatic dust detection.

## Output bit depth
- The scan is always taken at the profile's depth (the transparency unit delivers 16 bit anyway); the **file** depth is separate: `latent_image_edit::BitDepth` (`Sixteen` default, `Eight`), `write_image_depth` (`write_image` = 16 bit), `to_8bit` rounds `v * 255 / 65535`. The conversion is the very last step, after crop/rotate/tone/sharpen, so the finished look is quantised once (no dithering).
- GUI: **Bit depth** combo next to Format (`ScanUi::depth` -> `ScanRequest::depth` -> `worker::save_frame`); remembered in `settings.toml` `[save] eight_bit`. CLI: `scan --depth 8|16`.
- Editor: **Save as 8 bit** (`Edits::eight_bit`, a pending edit) halves a 16-bit file when applied; Restore original brings the 16 bit back. An 8-bit file (`latent_image_edit::file_depth` reads the header) stays 8 bit on every Apply, so editing never silently doubles it (the box is shown ticked and disabled).

## Preview resolution
- The overview is scanned at the **Preview** dropdown's resolution (Scanner & profile, under Resolution; the source's own values between 150 and 1200 dpi, default the lowest of at least 150, i.e. 300 on the 9000F transparency unit; remembered as `preview_dpi` in `settings.toml`). `ScanUi::preview_dpi_for` rounds up to a value the source offers. The whole window at 600 dpi is ~5100 x 5900 px (~90 MB 8-bit), at 1200 dpi ~360 MB while scanning.
- The stored 16-bit overview is shrunk with `preview::downscale` (block **average**, not nearest pixel) to at most `worker::preview_max_side(dpi)`: 2048 px up to 300 dpi (as before), 4096 above, so a higher preview dpi really gives more pixels (600 dpi -> 2960 px) while slider drags, which re-render the whole overview, stay affordable. The editor's preview uses the same `downscale`.
